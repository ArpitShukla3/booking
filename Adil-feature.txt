3. TOOLS AND TECHNOLOGIES USED, AND WHY
================================================================================

BACKEND (backend/)
  Node.js 24 (.nvmrc 24.22.2)  Same runtime for everyone; Adil pinned it in .nvmrc so
                               "nvm use" picks the right version.
  Express 5                    HTTP server. Express 5 forwards rejected promises to the error
                               handler, so controllers need no try/catch.
  PostgreSQL 16 (Docker)       Durable state: everything survives a refresh and a backend
                               restart (an explicit acceptance criterion in every ticket).
  Knex 3 + pg                  Query builder + migrations. Every schema change is a numbered,
                               reversible migration; transactions via db.transaction().
  Zod 4                        Input validation with readable per-field messages
                               ({ error: { message, fields: { field: "reason" } } }).
  TypeScript via tsx           Services/controllers/types in .ts without a build step;
                               "npm run typecheck" runs tsc in noEmit mode.
  node:test + supertest        Built-in test runner (no extra framework); supertest calls the
                               Express app in memory for integration tests.

FRONTEND (frontend/)
  React 19 + Vite 8 + TS       Fast dev server and typed components.
  React Router 7               Routes such as /signup, /login, /dashboard, /my-requests,
                               /travellers/:id, /groups/:id/chat; RequireTraveller guards.
  Zustand 5                    Small global stores (signed-in traveller, demo traveller). No
                               boilerplate, easy to unit test with an injected API/storage.
  Axios                        One configured client (src/lib/api.ts) that adds the
                               X-Traveller-Id header and turns errors into ApiError.
  React Hook Form + Zod        Signup/login forms: client-side rules mirror the backend rules.
  Tailwind 3.4.17 + plain CSS  Booking.com look with theme tokens in index.css; feature CSS
                               files (groups.css, profile.css, chat.css). Tailwind is pinned.
  shadcn-style UI + lucide     Button, Dialog, Input, Select components and icons.
  Vitest                       Unit tests for pure logic (vote rules, button states, chat maths).
  Playwright                   Browser tests against the real backend + database.
  Oxlint                       Linter (the project uses Oxlint, not ESLint).

WHY THIS SET
  - Project rules (AGENTS.md / Agent.md) fix the stack; Adil kept to it.
  - No AI/LLM calls at runtime, no passwords/JWT/OAuth (demo identity = Traveller ID).
  - Business rules live only in backend services, so the frontend can never bypass them.

4. ARCHITECTURE ADIL FOLLOWED
================================================================================

BACKEND: router -> controller -> service -> helper  (Agent.md section 4.1)

  routes/<f>.routes.js          URL + middleware (requireTraveller) -> controller
  controllers/<f>.controller.ts Read req, call ONE service, send status + JSON. No logic.
  services/<f>.service.ts       ALL business rules, validation, transactions, HttpError.
                                Exported as one object so unit tests can mock.method() it.
  helpers/postgres/<f>.helper.js The ONLY place with SQL (Knex). Optional trx parameter last.
  validation/<f>.validation.ts  Zod schemas.
  types/<f>.ts                  Row and DTO types.

  Identity: middleware/currentTraveller.js reads the X-Traveller-Id header, checks the
  traveller exists (401 otherwise) and sets req.traveller.

  Errors: services throw HttpError(400/403/404/409); middleware/errorHandler.js turns them
  into { error: { message, fields } }.

FRONTEND
  src/features/<feature>/   Pages, components, pure logic (+ .test.ts) and CSS per feature.
  src/services/*Service.ts  Typed promise API per backend feature; components only call these.
  src/types/*.ts            DTO types matching the backend.
  src/store/*.ts            Zustand stores for global state.
  src/lib/                  api.ts (Axios), useAsync.ts (data loading), identityStorage.ts.

WORKFLOW
  Backend: tests first (low = unit with mocked helpers, mid = HTTP integration on the test
  database booking_test), then helper -> service -> controller -> route.
  Every feature: ticket in tasks/, contract in tasks/PLAN.md, docs in Agent.md and
  docs/PROJECT_CONTEXT.md.

6. FEATURE 2 - M1 SIGN UP / SIGN IN WITH 7-DAY REMEMBERED IDENTITY (2b658a4)
================================================================================

WHAT THE USER SEES
  /signup     Form: name, age, gender, home city, 3-letter airport code, interests (loaded
              from the real catalog), gender preference. Success shows the new Traveller ID.
  /login      Sign in by Traveller ID only (e.g. T-025). No password (demo identity).
  /dashboard  Protected profile page: ID with copy button, details, interests, expiry time of
              the remembered sign-in, logout.
  Header      Shows the signed-in name + Logout, or Register / Sign in.

BACKEND
  Endpoints
    POST /api/travellers               Create profile -> 201 Traveller (DB generates the ID)
    POST /api/travellers/sign-in       { traveller_id } -> 200 Traveller, or 404 "not found"
    GET  /api/travellers/:traveller_id Profile restore -> 200 or 404
    GET  /api/interests                Interest catalog (ID, label, category)
  Rules (services/travellers.service.ts)
    - Zod validation (validation/travellers.validation.ts); IDs must match T-<3+ digits>.
    - Interests must exist in the catalog -> 400 with a field message.
    - Unique violation (23505) -> 409; any other DB failure -> readable 503.
  Database
    Migration 20261113000003_traveller_id_sequence.js
      - traveller_id_seq starting after the highest seeded ID (T-024), next_traveller_id()
        produces T-025, T-026, ... (width grows after 999, never truncated)
      - travellers.traveller_id DEFAULT next_traveller_id(): the DB, not the client, makes IDs.
    Migration 20261113000004_backfill_missing_travellers.js
      - Inserts any missing seed travellers/interests without overwriting profiles and moves
        the sequence forward (never backwards). Also: scripts/seed-travellers.js
        ("npm run seed:travellers").

FRONTEND
  Files  features/identity/{SignupPage, LoginPage, DashboardPage, session, schemas,
         CopyTravellerId}.tsx, store/useTravellerStore.ts, lib/identityStorage.ts,
         services/travellerService.ts, lib/api.ts
  Forms  React Hook Form + zodResolver; the signup schema is built from the live interest IDs.
         Backend field errors are shown next to the fields; input is kept on error.

STATE MANAGEMENT (the core of M1)
  useTravellerStore (Zustand) is the ONLY owner of identity:
    state:   traveller, travellerId, expiresAt, isLoading, isInitialized, restoreError,
             storageWarning, notice
    actions: signup(), signInWithId(), restoreSession(), logout(), ensureValidSession()
  Persistence: localStorage key "group_match_active_traveller" stores ONLY
    { traveller_id, expires_at }. The profile itself always comes from PostgreSQL.
  Rules:
    - Only signup or an explicit sign-in starts a new 7-day deadline. Restoring on refresh
      never extends it.
    - readIdentity() validates the stored JSON (format, ID pattern, safe integer, not expired);
      corrupt or expired data is cleared.
    - Backend 404 on restore -> logout with a message. Network/5xx -> keep the identity and show
      "Try again" (temporary outage does not sign you out).
    - Race protection: an "operation" counter discards late responses (e.g. logout during a
      slow sign-in).
    - If localStorage can't be written, the user is told to save their Traveller ID.
  Lifecycle (features/identity/session.tsx):
    - SessionLifecycle: restores on load; checks expiry on window focus and when the tab
      becomes visible; a timer logs out exactly at expiry; "storage" events sync other tabs.
    - RequireTraveller: loading -> spinner; restore error -> retry screen; signed out ->
      redirect to /login.
    - HomeSessionRedirect: signed-in users visiting "/" go to /dashboard.
  Request identity: lib/api.ts adds X-Traveller-Id to every Axios request from the store.

WHY THIS DESIGN
  The task required real persistence, a seven-day remembered identity and no passwords, JWT,
  OTP or OAuth. Storing only the ID + deadline keeps the browser copy minimal; the database stays
  the source of truth.

TESTS  backend/tests/unit/services/travellers.service.test.js,
       backend/tests/integration/travellers.api.test.js,
       frontend/src/store/useTravellerStore.test.ts (time is injected, so expiry is tested
       without waiting 7 days), frontend/src/lib/api.test.ts, Playwright identity journeys.

8. FEATURE 4 - M5 JOIN REQUESTS + OWNER NOTIFICATIONS (2aa78ec)
================================================================================

WHAT THE USER SEES
  Seeker (group page /groups/:groupId):
    "Interested" button. Disabled with a reason when: you organise the trip, you're already a
    member, "Request pending", "Request declined", "Removed from group", or "Group is full".
  Seeker (/my-requests):
    Every request with group, dates, members, status pill and filter
    (All / Pending / Approved / Declined / Removed).
  Owner:
    - Header bell with the number of pending requests (refreshes on each navigation).
    - My groups: notification panel "N travellers want to join your trips" (name, age, gender,
      city, shared interests, time ago, Review button) and a red badge per owned group.
    - Group page "Join requests" section: seeker card with age, gender, home city, gender
      preference, interests (shared ones highlighted), Approve / Decline (Decline asks for
      confirmation); decided requests under "Past decisions".

BACKEND
  Endpoints (all need X-Traveller-Id)
    POST /api/groups/:groupId/join-requests      seeker sends request -> 201 PENDING
    GET  /api/groups/:groupId/join-requests      owner only -> requests + seeker + shared
    POST /api/join-requests/:requestId/approve   owner only, transaction, 409 if full
    POST /api/join-requests/:requestId/reject    owner only
    GET  /api/join-requests/mine                 seeker's requests + group summary
    GET  /api/join-requests/incoming             owner notifications (pending on owned groups)
  GET /api/groups/mine now returns the real pending_requests count.
  Rules (services/joinRequests.service.ts)
    - requestBlocker(): OWNER / MEMBER / PENDING / REJECTED / REMOVED / FULL -> 409 + message.
    - One request per (group, seeker): UNIQUE constraint + INSERT ... ON CONFLICT DO NOTHING,
      so double clicks never create duplicates.
    - Approve: one transaction -> lock the group row (SELECT ... FOR UPDATE), lock the request,
      must still be PENDING, re-check size, append to groups.member_ids, set APPROVED.
      Concurrent approvals for the last spot: exactly one succeeds, others get 409 "full".
    - Only the owner can list/approve/reject (403 otherwise).
  Database
    Migration 20261113000007_create_join_requests.js: join_requests (request_id R-1001+,
    group_id, seeker_id, status, created_at, decided_at), UNIQUE(group_id, seeker_id),
    CHECK status, CHECK decided_at is NULL exactly while PENDING.

FRONTEND
  services/joinRequestService.ts, types/joinRequest.ts,
  features/groups/joinRequests.ts (pure seekerAction() + labels + timeAgo),
  features/groups/requestParts.tsx (InterestPanel, OwnerRequestsSection, IncomingRequestsPanel),
  features/groups/MyRequestsPage.tsx, changes in GroupPage.tsx, MyGroupsPage.tsx,
  BookingHeader.tsx (bell + "My requests" nav), common.tsx (InterestTags highlight).

STATE MANAGEMENT
  - Server state loaded with useAsync(read, key): cancellable, retry(), stale responses ignored.
  - After approve/decline the decision is kept in local component state ({ request_id: status })
    so the list updates instantly without a reload flash; the group is re-fetched silently
    ("fresh" state in GroupPage) so members/seat bar update.
  - Header bell re-reads incoming requests when the route changes (key includes pathname).

TESTS  Backend unit joinRequests.service/controller + groups.service; integration
       joinRequests.api.test.js (Scenario B Priya -> Sarah approves -> 2/3, duplicates,
       reject, 403, full-group overflow, concurrent approvals). Frontend joinRequests.test.ts,
       Playwright joinRequests.spec.ts.

11. FEATURE 7 - S1 TEAM CHAT (803d828)
================================================================================

WHAT THE USER SEES
  Group page sidebar: "Chat with team". Disabled (with a lock and reason) until the group has
  booked its hotel; afterwards it opens /groups/:groupId/chat.
  Chat page:
    - Header: group name, Chat ID (C-1001...), members, current access settings.
    - Messages with sender, "Organiser" tag, MESSAGE ID (M-1001...), CONTENT and TIME; day
      separators (Today / Yesterday / date). Mine on the right in blue.
    - Announcements: highlighted yellow card (organiser only).
    - Polls: question + 2-6 options, bars with %, total votes, "your vote"; tap another option
      to change your vote.
    - Composer tabs: Message / Announcement / Poll (locked tabs explain why).
      Enter sends, Shift+Enter new line, 2,000 character counter.
    - Owner: "Group settings" dialog: who can send messages, who can create polls
      (All members / Only the organiser). Members can always vote.
SIMPLE ACCESS SYSTEM
  Action               Owner     Member
  Send messages        always    if messaging = ALL_MEMBERS (default)
  Create polls         always    if polls = ALL_MEMBERS (default)
  Announcements        always    never
  Vote in polls        always    always
  Change settings      always    never
BACKEND (mounted at /api/groups/:groupId/chat, all need X-Traveller-Id)
  GET    /                         chat id, settings, my_permissions, members
  PATCH  /settings                 owner only: { messaging?, polls? }
  GET    /messages?after=M-...     oldest first (latest 200 without "after")
  POST   /messages                 { type: TEXT | ANNOUNCEMENT, content } -> 201
  POST   /polls                    { question, options[2..6] } -> 201 (one transaction)
  POST   /polls/:messageId/vote    { option_id } -> one vote per person, can be changed
  Gate on every call: group exists (404) -> caller is a member (403; removed members lose
  access) -> group has a booking (409). The chat row is created on first open (safe under
  concurrent opens: INSERT ... ON CONFLICT DO NOTHING).
  Pure rules in services/groupChat.service.ts: permissionsFor(), seqOf(), toMessageDto().
DATABASE  Migration 20261113000010_create_group_chat.js
  group_chats        chat_id C-1001+ (sequence), group_id UNIQUE, messaging, polls (CHECK)
  chat_messages      seq bigserial (START 1001), message_id GENERATED ALWAYS AS 'M-' || seq,
                     type CHECK, content 1..2000 CHECK, created_at
  chat_poll_options  option_id, message_id, label, position (unique per poll)
  chat_poll_votes    PRIMARY KEY (message_id, voter_id) -> one vote each, upsert to change
FRONTEND  features/chat/GroupChatPage.tsx, chatLogic.ts (+ test), chat.css,
          services/chatService.ts, types/chat.ts, GroupPage.tsx (button), App.tsx (route).
STATE MANAGEMENT
  - Chat + messages in page state. Every 4 seconds (only while the tab is visible) it re-reads
    the latest page of messages and the chat (permissions/settings) and merges them by
    message ID (mergeMessages() dedupes and sorts numerically, so M-999 < M-1000).
  - Optimistic poll votes (applyPollVote()) with rollback on error; polling pauses while your
    own vote is saving so the number doesn't jump back.
  - Auto-scroll to the newest message unless the user scrolled up to read.
  - If the owner changes settings, the member's composer switches to an allowed tab.
BUGS FOUND BY TESTS AND FIXED
  - Message IDs could restart at M-1 after TRUNCATE ... RESTART IDENTITY -> sequence START 1001.
  - Other members didn't see updated vote counts -> poll the latest page, not only newer ones.
TESTS  groupChat.service/controller unit tests, groupChat.api.test.js (7 cases),
       chatLogic.test.ts, Playwright chat.spec.ts (4 journeys incl. two users chatting).

TESTS     joinRequests.service + groups.service unit tests, 5 new integration cases,
